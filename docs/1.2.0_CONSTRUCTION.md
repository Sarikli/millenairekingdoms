# Royal construction: implemented request boundary

Current implementation is internal and not connected to player packets/GUI or the NPC scheduler. It is not dev.3 or
completed 1.2.0. Read the full requirements, progress and payment policy before extending it.

## Implemented

- RoyalConstructionCatalog authorizes the current player/NPC ruler and kingdom member, rejects local/player control,
  and previews same-culture new-building candidates from the original normal-growth tier/count/tag/cooldown logic.
  NormalGrowthBridge pins exact 9.0.3 private signatures. No new Mixin or copied growth algorithm.
- RoyalConstructionStore binds the complete order ID/dimension/kingdom/capital/village/actor/tenure/type/plan/variant/fee
  and original building UUIDs in its own strict atomic index before any payment. One active order per village, immutable
  quote, guarded stages, retained terminal IDs and fail-closed unknown/future/corrupt data. Political format remains 6.
- RoyalVillagePersistence uses the original VillageSavedData serializer and waits for the asynchronous NeoForge worker,
  then reads the actual saved pending/building metadata. Future/corrupt original files are protected before saving.
- RoyalConstructionService now accepts/retries internal player/NPC requests. It takes only a selected plan-set ID and
  request UUID; it chooses the variant/price/initial identities on the server. Inactive/unloaded villages and existing
  natural pending work reject a new request before charging. A genuine nonempty template and normal resource costs
  must be enabled. It does not place blocks, spawn builders, grant resources, set ownership or choose a location.

## Current acceptance/retry protocol

1. Validate real agency, membership, reputation, village control/type, active state, current normal eligibility and template.
2. Atomically reserve the village with REQUESTED and the immutable intent. A retry loads that stored quote before taking
   another variant/price; fee configuration changes affect only new orders.
3. Use the shared real-coin payment with the order UUID as both payment ID and CONSTRUCTION reference. Only PAID advances
   the order. A conflicted/refunded/unexpected payment cannot become a free order.
4. Revalidate and write QUEUING before touching the engine. Fill an EMPTY normal PendingProject slot with no location,
   upgrade or player ownership. Wake the normal growth cache; never overwrite a natural project.
5. Await the original SavedData worker and exact disk read-back. Only then write QUEUED and commit patronage.
6. Interrupted QUEUING retries adopt the exact saved/live pending project or a unique new matching engine building UUID
   outside the original set. Different natural work is preserved. Ambiguous multiple buildings quarantine the order.
7. Authorized receipt inspection does not touch chunks. A proven queued receipt may be committed after restart without
   charging again. A mismatched actor/kingdom/capital/reference/purpose/amount cannot satisfy the request.

The normal engine later chooses the site, demands resources and runs builders. This first service unit does not yet
monitor that work to completion. It deliberately never marks an order COMPLETED from a pending record or test fixture.

## Required before exposing gameplay

- Durable cancellation decisions and exact refund policy: pre-acceptance refunds; accepted patronage is nonrefundable.
  Do not clear unrelated pending work or demolish/freeze an autonomous building after cancellation.
- Authority/membership/capital/abdication/destruction cleanup, including same-tick abdicate/reclaim retirement and offline
  player handling. An offline player order must never be resumed through NPC spending.
- Startup/tick recovery and genuine QUEUED/IN_PROGRESS/BLOCKED/COMPLETED monitoring, bounded retries/diagnostics, missing
  resources/space handling and natural fallback growth. No global per-tick terrain/inventory scans or forced remote loads.
- Real builders/material consumption/placement and completion tests; cross-file abrupt interruption tests between order,
  payment and original village saves. The earlier four payment-only abrupt probes are not this domain guarantee.
- EN/TR GUI/payloads, permissions/replay tests, progress/reasons, later NPC policy integration and full regression/balance.

Current focused evidence is **19 required tests in write and 19 in separate reload**, plus normal build. Four new tests
use real coins/chests and actual original pending persistence: acceptance/replay, natural/unloaded rejection, failed
domain acknowledgement with unchanged quoted price, and separate-JVM paid queue recovery. They do not assert real NPC
building completion. No scheduled/player-facing paid construction feature is advertised yet.

## Durable cancellation (current)

Order index format 2 retains `cancellationFrom` before any financial operation. Strict v1 read migration preserves every
intent/stage/building and terminal identity. Reads never rewrite legacy bytes; the next locked atomic mutation writes v2.
An unresolved v1 CANCELLING entry explicitly retains an unknown origin rather than assuming it is refundable.

Internal cancelNpc/cancelPlayer and retry support REQUESTED/PAID refunds, including a payment persisted before order PAID
and an interrupted PREPARED debit. A full/unloaded treasury defers financial work with the CANCELLING decision intact.
Exact purpose/reference/amount/actor validation prevents refunding an unrelated colliding payment UUID. Once QUEUED or
IN_PROGRESS, patronage is earned/nonrefundable: cancellation stops royal tracking and preserves autonomous pending work,
existing building identity and builders. Nothing clears an original engine project or demolishes a building.
QUEUING publication can span independent saves; cancelling it (or a legacy unknown-origin cancellation) conservatively
retains RECOVERY_REQUIRED + AMBIGUOUS_ENGINE_STATE and the reservation/receipt. A coincident matching natural plan does
not justify either a refund or destructive queue removal. An audited recovery path remains a hardening gate.

Focused evidence: **30+30** in fresh `royal-cancellation-03`, normal build passed, under
`verification/1.2.0/royal-cancellations/`. No autonomous builder completion or player GUI is claimed.
