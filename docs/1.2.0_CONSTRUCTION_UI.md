# Royal construction screen / Kraliyet inşaat ekranı

Latest RC.7 behavior: open **Rulership → Construction**. While the village's ordinary job is pending, **Queue / Sıraya al** saves an unpaid persistent WAITING mandate; after completion, the actual online original ruler and available target/treasury allow automatic revalidation and single payment/publication. Insufficient money or changed plan eligibility stays visible and unpaid; cancellation preserves native work. See the [queue protocol](1.2.0_CONSTRUCTION_QUEUE.md), including format4/downgrade details. Network protocol3 remains unchanged; matching client/server builds are required. Below is the earlier dev.3 screen protocol/evidence history.

The dev.3 construction milestone adds a Construction tab to the existing kingdom screen. All previous tabs/actions
remain available. This is a development milestone; shipments, NPC economic policy and the remaining 1.2.0 integration
are not finished. Client and server must both use the matching development build (network protocol 2).

## Player use

1. Open the existing kingdom screen and select Construction. You must currently rule an active kingdom and have the
   normal decision reputation at its capital. Other viewers receive an explanatory disabled view, not private offers/funds.
2. Cycle the village selector to choose a member village. Its present availability is displayed independently of the
   saved order reason. Only the selected village's normal growth catalog is evaluated; distant chunks are not forced.
3. Select an original native building plan and review the denier patronage fee. The treasury must contain real spendable
   currency; undelivered taxes/custom protected coins are not a replacement. Hover for the full plan name/unavailable reason.
4. Commission the plan. The server rechecks agency, membership, culture/type, normal growth/count/cooldown eligibility,
   current price and real payment. The village retains NPC control, chooses its own legal location and uses real materials
   and original builders. Paying patronage does not supply building goods or instant construction.
5. Refresh to follow the saved stage, current obstacle and native work progress. Progress includes terrain preparation;
   it is not a percentage of finished visible template blocks. Native engine/world-save acknowledgement is still required
   before royal COMPLETED. Missing resources, unavailable space/builders/chunks and explicit recovery are separate states.
6. Resume saved order retries the existing UUID after an incomplete request/cancellation. It does not create another
   purchase at a new price. Cancel tracking asks for confirmation and preserves the village's own autonomous work.

Before acceptance, cancellation can refund only actual previously paid patronage to original available treasury storage;
full/unloaded storage defers rather than discarding goods. After durable acceptance, patronage is earned and retained.
Uncertain publication remains operator-reviewed recovery instead of guessing a refund or deleting a natural project.
An operator may use the [audited maintenance protocol](1.2.0_RECOVERY.md); player payloads cannot invoke OP recovery.

itibarını sağlamanız gerekir. Köy seçicisiyle bağlı bir köye geçin; uygun özgün planı ve denier cinsinden destek bedelini
inceleyin. Düğmenin açıklaması eylemin neden kullanılamadığını gösterir. Vergi alacağı, gerçek harcanabilir hazine parası değildir.

Sipariş verildiğinde bütün yetki, köy, kültür, uygunluk ve ödeme denetimleri sunucuda tekrarlanır. Köy bağımsız yönetimini
korur; konumu kendi seçer, gerçek malzemeyi ve özgün NPC inşaatçıyı kullanır. Destek bedeli malzeme veya anında bina satın almaz.
Durumu görmek için yenileyin. İş yüzdesi arazi hazırlığını da içerir; görünür bina bloklarının tamamlanma yüzdesi değildir.

Kayıtlı işleme devam et, aynı siparişi sürdürür ve yeni bedelle ikinci sipariş açmaz. Takibi iptal et onay ister: henüz
kabul edilmemiş gerçek ödeme, özgün depoya erişilebildiğinde iade edilebilir; kabul edilmiş destek iade edilmez. Köyün
kendi işi iptal edilmez. Belirsiz kayıtlar için operatör incelemesi gerekir. Bir hata mesajı işlem kısmen kalıcılaşmışken
“hiçbir şey değişmedi” demez; yenileyip kayıtlı durumu inceleyin.

## Offer and payload boundaries

Offers are bounded ephemeral server records, binding player connection/UUID, dimension, active kingdom/capital/tenure,
selected village, plan and quoted fee. The server issues the request UUID and expires new offers after 1200 game ticks.
Price changes reject before intent/payment; current server catalog prices remain authoritative. A saved existing order
ID instead reuses its original immutable fee/variant and full agency binding, even after cache loss/restart/offer expiry.
Used IDs rotate out of new offers; old terminal IDs remain immutable replay tombstones. A cancelled unpaid order can be
followed immediately by a new offer without reviving the old UUID. No client price/actor/variant is accepted as authority.

The shared action handler keeps its 4-tick per-player rate limit and server revalidation. The bounded action text codec
now accepts registry identifiers up to 128 characters; protocol 2 rejects incompatible protocol-1 clients. Cancellation
and resume delegate to the same tested domain services. Only a selected village's catalog is read; there is no new
global per-tick GUI scan. Future/corrupt/locked order data yields unavailable/unknown state, never an empty registry or
an enabled purchase. Original data remains untouched. Political format6, payment1 and order3 are unchanged by this UI.
