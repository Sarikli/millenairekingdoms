# Royal shipments: implementation boundary

Current phase4 work has **pure goods-slot plans and read-only authorized native stock**, still dev.3. It is not a live shipment or durable escrow.
Full acceptance criteria remain in requirements phase4; normal autonomous trade must stay unrestricted. No mandatory
market, shared instant stockpile or physical merchant/caravan requirement is introduced.

## Implemented primitive

RoyalGoodsPlan.remove computes exact ordinary-chest before/after/cargo stacks for one native item/component prototype
and positive bounded quantity. It preserves every unrelated item/component, splits actual source stacks in slot order,
and rejects insufficient stock without returning a partial plan. insert computes full capacity for all exact cargo,
merges only native item/component-equal stacks and respects native stack limits/ordinary-chest64 limits. Full destinations,
unstackable goods, empty/invalid quantities and overstacks fail before live mutation. Inputs and all returned snapshots
have no mutable aliases; matchesBefore rejects changed source inventories. Limits are4096 slots /1,000,000 requested items.

The planner has no world references, authorization, quote, fee, source-reserve calculation, transaction UUID, timer,
container identity or journal. A caller cannot treat an insertion plan as proof that cargo was actually debited.
No production packet/tick/NPC consumer applies these plans yet.

Fresh verifyRoyalGoods / royal-goods-plan-01: both separate JVMs logged **All 8 required tests passed**, normal build
passed. Pure tests cover exact quantities/components, unrelated stock, capacity, invalid inputs, defensive snapshots,
unstackable items and100 deterministic slot cases. This is not a hundred-day game simulation.

A test-only helper explicitly applies plans to two actual chests in separate chunks and acknowledges native saves:
source64 ->24, destination4 ->44, total68 spruce logs; unrelated diamonds3/emeralds4 survive. Another JVM reloads those
actual images without repair. This graceful primitive image test is not proof of safe cross-file domain transfer,
abrupt termination, cargo escrow, fees, player permissions or NPC shipping. Evidence: verification/1.2.0/royal-goods-plans/.

## Next required layers

1. Authorized read-only real village storage/surplus is implemented below. Actual dispatch must recheck the current
   native reserve inputs and storage images, not just trust a prior preview.
2. A strict versioned immutable shipment intent/escrow, physical identities/full images and unresolved container guards.
   Source removal, destination insertion, financial receipt and journal are independent files. Actual acknowledged
   writes/read-back and before/after reconciliation are required; unexpected third images stay quarantined intact.
3. Real existing-capital transport fees, timed transit, loaded/full delivery/return deferral, immutable request replay,
   cancellation, authority/membership/capital/kingdom fall and original-village loss. No refund redirection or guessed cargo.
4. Actual abrupt-process cuts and separate-JVM recovery at debit/escrow/delivery/return/fee boundaries, then bounded
   runtime and EN/TR player UI. Shared NPC consumers come later and must use the same conserving paid service.

The exact durable state model must follow inspected APIs and tested failure outcomes. Do not describe raw SavedData
booleans or graceful chest saves as exactly-once delivery. Preserve ambiguous goods/coins and diagnose them explicitly.

## Authorized native surplus (implemented)

RoyalVillageStock binds the current active kingdom/member, player ruler/reputation/dimension/tenure/capital or legitimate
NPC agency. NPC decisions cannot use a player-controlled/local-player-owned village or a player-ruled kingdom. Explicit
player royal stock access follows political membership. Current native village type/local owner/storage references are
captured and revalidated; no village owner changes. Quotes require the village and every declared chest/furnace/firepit
position already loaded. Connected chest halves are verified/deduplicated, with exact block states/BE identity/all slots.
Unknown/custom storage, changed containers/content, unloaded positions and unknown work requirements preserve stock.

A narrow pinned9.0.3 read-only adapter accesses the original private furnace/firepit position lists; it never calls native
loadChunks. Native inventory cache is refreshed before inspecting native counts/export. Only ordinary default-component
noncurrency chest goods are removable. Furnace/firepit output and custom/protected stacks cannot back removable goods.
Native export protects culture targets and townhall household needs, but its construction reservation depends on builder
assignment and does not apply generic anywood to an arbitrary actual log item. This adapter additionally protects full
costs of every being-built instance, pending work and all known controlled-queue entries, and native required goods for
households throughout the village. Every log species retains the full relevant anywood demand, conservatively.

For each product, retained ordinary stock is the maximum of native protected quantity, full construction + culture target
+ all households, and the configured minimum remainder. Available is max(0, exact removable chest quantity - retained).
Full costs stay protected even when a builder already carries materials; this may retain more than the original helper.
The source's own needs never rely on furnace/custom/unremovable counts to justify exporting its ordinary goods.
Gameplay config royalShipments.minimumStockRemaining defaults16 (0..65536); maximumQuantity defaults4096 (1..65536)
for the future consumer. These settings do not enable shipments or alter taxes/pricing. Limits:128 physical chest halves,
256 auxiliary positions per kind,256 controlled queued projects. Unknown larger shapes fail closed without rewriting data.
