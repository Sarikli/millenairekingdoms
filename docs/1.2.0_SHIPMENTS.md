# Royal shipments: implementation boundary

Current phase4 work has **pure goods-slot plans, read-only authorized native stock and a strict shipment ledger**, still dev.3. It is not a live shipment or durable escrow.
Full acceptance criteria remain in requirements phase4; normal autonomous trade must stay unrestricted. No mandatory
market, shared instant stockpile or physical merchant/caravan requirement is introduced.

## Implemented primitive

RoyalGoodsPlan.remove computes exact ordinary-chest before/after/cargo stacks for one native item/component prototype
and positive bounded quantity. It preserves every unrelated item/component, splits actual source stacks in slot order,
and rejects insufficient stock without returning a partial plan. insert computes full capacity for all exact cargo,
merges only native item/component-equal stacks and respects native stack limits/ordinary-chest64 limits. Full destinations,
unstackable goods, empty/invalid quantities and overstacks fail before live mutation. Inputs and all returned snapshots
have no mutable aliases; matchesBefore rejects changed source inventories. Limits are4096 slots /1,000,000 requested items.

The planner has no world references, authorization, quote, fee, source-reserve calculation, transaction UUID, timer,
container identity or journal. A caller cannot treat an insertion plan as proof that cargo was actually debited.
No production packet/tick/NPC consumer applies these plans yet.

Fresh verifyRoyalGoods / royal-goods-plan-01: both separate JVMs logged **All 8 required tests passed**, normal build
passed. Pure tests cover exact quantities/components, unrelated stock, capacity, invalid inputs, defensive snapshots,
unstackable items and100 deterministic slot cases. This is not a hundred-day game simulation.

A test-only helper explicitly applies plans to two actual chests in separate chunks and acknowledges native saves:
source64 ->24, destination4 ->44, total68 spruce logs; unrelated diamonds3/emeralds4 survive. Another JVM reloads those
actual images without repair. This graceful primitive image test is not proof of safe cross-file domain transfer,
abrupt termination, cargo escrow, fees, player permissions or NPC shipping. Evidence: verification/1.2.0/royal-goods-plans/.

## Authorized native surplus (implemented)

RoyalVillageStock binds the current active kingdom/member, player ruler/reputation/dimension/tenure/capital or legitimate
NPC agency. NPC decisions cannot use a player-controlled/local-player-owned village or a player-ruled kingdom. Explicit
player royal stock access follows political membership. Current native village type/local owner/storage references are
captured and revalidated; no village owner changes. Quotes require the village and every declared chest/furnace/firepit
position already loaded. Connected chest halves are verified/deduplicated, with exact block states/BE identity/all slots.
Unknown/custom storage, changed containers/content, unloaded positions and unknown work requirements preserve stock.

A narrow pinned9.0.3 read-only adapter accesses the original private furnace/firepit position lists; it never calls native
loadChunks. Native inventory cache is refreshed before inspecting native counts/export. Only ordinary default-component
noncurrency chest goods are removable. Furnace/firepit output and custom/protected stacks cannot back removable goods.
Native export protects culture targets and townhall household needs, but its construction reservation depends on builder
assignment and does not apply generic anywood to an arbitrary actual log item. This adapter additionally protects full
costs of every being-built instance, pending work and all known controlled-queue entries, and native required goods for
households throughout the village. Every log species retains the full relevant anywood demand, conservatively.

For each product, retained ordinary stock is the maximum of native protected quantity, full construction + culture target + all households, and the configured minimum remainder. Available is max(0, exact removable chest quantity - retained).
Full costs stay protected even when a builder already carries materials; this may retain more than the original helper.
The source's own needs never rely on furnace/custom/unremovable counts to justify exporting its ordinary goods.
Gameplay config royalShipments.minimumStockRemaining defaults16 (0..65536); maximumQuantity defaults4096 (1..65536)
for the future consumer. These settings do not enable shipments or alter taxes/pricing. Limits:128 physical chest halves,
256 auxiliary positions per kind,256 controlled queued projects. Unknown larger shapes fail closed without rewriting data.

## Strict durable ledger (implemented, metadata gate only)

RoyalShipmentStore format1 binds the full immutable mandate/route/original identities/server product/price/quantity/time.
PREPARING -> COLLECTING -> IN_TRANSIT -> AWAITING_DELIVERY -> DELIVERED is the normal lifecycle; cancellation/retirement
permanently requests RETURNING, then CANCELLED only after all collected items are accounted and no physical operation
is pending. RECOVERY_REQUIRED never resets uncertain evidence. Cancellation provenance remains set even in quarantine.
Due time freezes at dispatch, based on the original duration, not issue time or replay/restart.

Each original container operation is PREPARED, APPLIED or CANCELLED (proved never performed). Only applied collections
back escrow; prepared deliveries/returns immediately reserve that escrow. Partial delivered/returned quantities remain
separate. Same operation IDs cannot change bindings, and unresolved positions OR physical UUIDs cannot overlap across
jobs. One active royal outgoing job/source limits contention; normal Millénaire trade remains unrestricted. Native full
slot NBT payloads are defensive and structurally versioned; the physical coordinator must additionally parse/check
actual stacks/direction/quantity with server registries before mutation. Never acknowledge an operation from stage names.

Atomic lock/fsync/rename/directory-sync index limits10k retained records/512 operations per record/16MB. Unknown/future/
corrupt data and file-lock failures preserve bytes. No automatic pruning/recreation of terminal operation history.
Fresh verifyRoyalShipments9+9/build passed; evidence royal-shipment-ledger contains actual pass lines. Its acknowledgements
are synthetic ledger inputs, so no physical stock/payment/escrow-crash/live delivery claim follows. Next wire the native
same-container proof coordinator, economic reservation guards and actual fees/time/return tests before player exposure.


## Native per-container cargo coordinator (implemented primitive)

RoyalCargoContainers validates native exact product/components/direction/quantity and all unrelated slots in a stored
operation. It shares royal_treasury identity1 and bound same-chest proofs with the corrected money coordinator, without
changing existing identity/journal/political formats or copying native serializers. plan acknowledges untouched BEFORE,
settle loads the durable row, defers unloaded storage, and applies a NEW delta only after current domain revalidation.
A synchronous mandate retirement during that callback is reloaded before the first slot write.

Native Items+proof write/flush/read-back precedes shipment-operation acknowledgement. Matching proof preserves current
contents after normal native consumption/deposits. Missing proof requires exact BEFORE; replacement/third/unknown
evidence is quarantined intact. Unperformed cancelled collection/delivery releases only its allocation after native
BEFORE/no-proof verification, never inventing return cargo. Durable APPLIED rows prevent stale-UUID replay after
cleanup. Only the owning acknowledged proof is cleaned; cleanup failure retains a safe financial result. The future
domain must also invalidate affected original BuildingInventory caches after mutation and enforce actual route/stock/
authority/fees, container reservations, time and retirement; this primitive has no player endpoint.

metadata/storage is real, but route/mandate/fee inputs are synthetic. No claim of authorized paid timed live delivery,

## Actual paid timed backend service (implemented)

RoyalShipmentService validates actual source native reserves/ordinary goods and current source/target political member
identities. Destination metadata may be unloaded at quote/issue; only later insertion waits for loaded active storage.
Full actor/tenure/type/townhall/center/local-owner/route/product/quantity/server-price/duration intent precedes the real
capital fee. No player-supplied price/distance/actor is trusted. Exact same-ID requests retain their quote and history.
One step performs one cargo/lifecycle boundary. Full collection precedes durable dispatch/due; its fee then becomes
nonrefundable and commits before delivery. Actual game time gates arrival; full/unloaded containers defer remaining
cargo, partial quantities stay accountable. Pre-dispatch cancellation returns acquired goods before actual fee refund.
Original capital ineligibility preserves liability; payment purpose/reference/actor/capital/amount never change.

Shipment governance joins the existing synchronous prepublication boundary without altering political format6. Both
endpoints/capital/kingdom/ruler changes retire old mandates before state publication; an index failure aborts publication.
Retired PREPARING retains its phase/flag until an in-flight fee finishes or proves absent, preventing an orphaned charge
when a temporary same-tick ruler is reclaimed. Existing paid offline work uses original UUID/tenure/reputation, with
new player fees requiring that original player online. No NPC impersonation/virtual shared inventory/market monopoly.
