# 1.2.0 — architecture and constraints

This document describes intended boundaries, not completed features. Follow [requirements](1.2.0_REQUIREMENTS.md).

## Compatibility foundation

Millénaire 9.0.3, Minecraft 1.21.1, Java 21. Keep NeoForge 21.1.259 until evidence requires otherwise.
Pin the original dependency checksum and preserve its JAR. Keep political format 6 and the existing atomic
kingdom/ruler/war transitions. The previous capital test fix waits for real chief entities, not merely terrain.

## Planned services

- Treasury spending: real coin inventories, shared player/NPC authorization and transaction IDs, explicit durable states.
- Construction adapter: inspect 9.0.3 planning APIs; request legal culture-compatible work without changing village ownership,
  clearing normal projects, instant placement, supplying free materials, or bypassing builders.
- Shipment service: source/destination validation, conservative reserves, durable escrow and an explicit recovery protocol.
  SavedData and chunk inventory saves are not cross-file atomic; do not promise exactly-once transfer without evidence.
- Personality: explicit mapping from capital village types; persistent base category with intentional invalid-type/capital handling.
- NPC policy: uses the same paid services, player-ruler exclusion, treasury reserve and cooldowns. War increases military weights
  for every personality without bypassing existing eligibility, truce, readiness or conquest rules.
- GUI/network: extend existing EN/TR screens, server-side revalidation, request deduplication and explanatory disabled actions.

Keep new economic lifecycles outside the already large KingdomSavedData. Use adapters at unstable dependency boundaries;
avoid unnecessary Mixins, forced chunk loading and global per-tick scans. Construction and shipments remain independent.

## Open engineering decisions

Actual construction insertion API, denomination-change semantics, escrow save ordering/recovery, order cancellation/refunds,
surplus calculation and full village-type mappings must be decided from the real 9.0.3 artifact and tested before implementation
is called complete. New storage needs explicit versions and fail-closed handling of unknown/future formats.

## Phase 2 implemented primitive

RoyalCoinPlan now computes immutable before/after slots with real MoneyHelper denominations and checked long arithmetic.
It conserves non-currency goods/components, protects custom-component coins, rejects insufficient funds and exact-change
capacity failures before mutation, and returns defensive snapshots. It has no permissions, world mutation, transaction IDs
or receipt semantics. Eight GameTests per JVM, including a real saved chest, passed.

## Durable-payment investigation (not implemented)

Do not wrap chunk mutations with a SavedData boolean and call it exactly-once. Minecraft's force-save path flushes chunk
workers, but chunk-save exceptions can be logged internally. A completion flag therefore needs evidence that the intended
container state actually reached disk, not just a successful method return. Consider a write-ahead journal with full
before/after slot images, per-container persistent identities (to detect destroyed/replaced chests), save/read-back barriers
and fail-closed recovery for a third/unexpected inventory state. Inventory changes and journal writes have no shared atomic
commit. Unloaded inputs must defer without forced loading. Recovery, interference, save failures, refunds and performance
costs must be tested before accepting this design or exposing paid gameplay. No such guarantees are established yet.

## Implemented journal primitive

RoyalPaymentJournal persists version-1 immutable request intent and guarded PREPARED/PAID/COMMITTED/REFUND_PREPARED/
REFUNDED/CANCELLED/RECOVERY_REQUIRED states. Exact request retries never reset the state; conflicting intent is rejected.
Atomic temporary-file replacement, file/directory force and real filesystem locks were tested on Linux. Future/corrupt
records are not overwritten. Seven journal tests plus eight coin tests passed in both JVMs. Other filesystem support
is unverified; unsupported atomic/durability primitives fail closed.

The journal does not know physical inventory state or validate financial authority. No live payment consumer exists.
In particular, calling transition(PREPARED, PAID) is not proof that coins were durably removed. The coordinator must
provide that evidence and test interruption boundaries before any paid action is exposed.

## Implemented authorized physical snapshot

RoyalTreasurySnapshot validates the existing active-kingdom/player reputation/NPC exclusion rules on the server thread.
It reads real loaded town-hall chests, includes both physical double-chest halves once, ignores undelivered tax as funds,
and returns defensive coin-slot snapshots. Revalidation rejects authority/reputation changes, capital/storage changes,
unloading, reconnection, replacement and any changed inventory slot. It does not mutate or force chunks.
Seven real-world fixture tests were added; the combined focused suite passed 22+22 across separate JVMs.
The existing FakePlayer helper is used only for player authority tests, not as proof of actual NPC work.

Remaining coordinator requirements: durable per-container identities (runtime object equality is insufficient across JVMs),
full immutable request binding, before/after recovery images, per-capital unresolved-payment serialization, physical save
confirmation, refund policy and interruption/I/O failure tests. No new live paid action is enabled at this checkpoint.
