# 1.2.0 — architecture and constraints

This document describes intended boundaries, not completed features. Follow [requirements](1.2.0_REQUIREMENTS.md).

## Compatibility foundation

Millénaire 9.0.3, Minecraft 1.21.1, Java 21. Keep NeoForge 21.1.259 until evidence requires otherwise.
Pin the original dependency checksum and preserve its JAR. Keep political format 6 and the existing atomic
kingdom/ruler/war transitions. The previous capital test fix waits for real chief entities, not merely terrain.

## Planned services

- Treasury spending: real coin inventories, shared player/NPC authorization and transaction IDs, explicit durable states.
- Construction adapter: inspect 9.0.3 planning APIs; request legal culture-compatible work without changing village ownership,
  clearing normal projects, instant placement, supplying free materials, or bypassing builders.
- Shipment service: source/destination validation, conservative reserves, durable escrow and an explicit recovery protocol.
  SavedData and chunk inventory saves are not cross-file atomic; do not promise exactly-once transfer without evidence.
- Personality: explicit mapping from capital village types; persistent base category with intentional invalid-type/capital handling.
- NPC policy: uses the same paid services, player-ruler exclusion, treasury reserve and cooldowns. War increases military weights
  for every personality without bypassing existing eligibility, truce, readiness or conquest rules.
- GUI/network: extend existing EN/TR screens, server-side revalidation, request deduplication and explanatory disabled actions.

Keep new economic lifecycles outside the already large KingdomSavedData. Use adapters at unstable dependency boundaries;
avoid unnecessary Mixins, forced chunk loading and global per-tick scans. Construction and shipments remain independent.

## Open engineering decisions

Actual construction insertion API, denomination-change semantics, escrow save ordering/recovery, order cancellation/refunds,
surplus calculation and full village-type mappings must be decided from the real 9.0.3 artifact and tested before implementation
is called complete. New storage needs explicit versions and fail-closed handling of unknown/future formats.
