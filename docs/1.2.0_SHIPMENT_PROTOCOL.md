## Why physical receipts are needed

Before/after inventory equality alone cannot prove whether an operation already happened if ordinary NPCs subsequently
consume/replenish goods. Do not freeze normal trade or infer ownership of cargo merely from matching quantities.
The proposed primitive stores a bound operation receipt in the **same chest block-entity NBT as its item changes**,
using original serializers and acknowledged chunk write/read-back. A matching durable receipt then proves that group's
operation applied even if legitimate contents later change. Chest identity/position/dimension and immutable binding
must match; unknown tags/replacement preserve evidence and stop speculative writes. This assumption needs real cuts,
including a halt between slot mutation and receipt assignment, before it can be claimed supported.

Inspect the existing physical UUID implementation in RoyalTreasuryImage (royal_treasury format1) before adding a shared
identity adapter. Preserve that format/key and existing receipts. Avoid duplicate competing IDs or an aesthetic rewrite
of tested payment code. Original ItemStack/BE/chunk serializers own data; no original JAR change or new Mixin is planned.

## Ledger and operation boundaries

- Persist a strict versioned full shipment intent before fees/goods: request UUID, dimension, kingdom/original capital,
  original actor/tenure, source/destination village/type/townhall/local-owner identities and centers, server product/quantity,
  fee, issue time and distance-derived duration. Reject conflicting retries and retain terminal IDs.
- Charge the existing real-capital SHIPMENT_FEE receipt under the same shipment reference. Never infer payment from a
  ledger stage name. Existing offline acknowledgement/refund needs full original purpose/capital/actor/amount binding.
- Revalidate actual native surplus and current mandate immediately before source preparation. Allocate immutable unique
  per-container operation IDs, exact cargo quantities, identities and full before/after images. Journal them durably first.
- Apply one loaded ordinary chest group on the server thread. Absent receipt requires exact validated before state.
  Set the exact after slots and matching receipt before the first native serialization, then flush/read back. Never
  overwrite unknown receipt data. A valid already-applied receipt acknowledges the existing operation without applying
  the item delta again. An unreceipted unexpected state remains explicit recovery until a safe reviewed retry is defined.
- Track applied source, destination and return groups separately. Spendable escrow is acknowledged removed quantity
  minus acknowledged delivered/returned quantity; retained history is never counted as reusable stock. Pending target
  allocations reserve that remaining quantity and cannot overlap or exceed it.
- Full source collection is dispatch acceptance; clearly define/translate when its administrative transport fee becomes
  nonrefundable. Before acceptance, cancellation returns only goods actually acquired and refunds only actual paid fees
  to the original eligible treasury. Fallen/moved capital liabilities remain explicit; never redirect refunds to a victor.
- Timed transit has a durable due game time. Unloaded/full target defers without forced chunks. Revalidate recipient
  membership/identity before delivery; ownership loss can require return to the original source, not a fabricated village.
  Partial delivery must report delivered and returned amounts explicitly; already delivered/consumed goods cannot be recalled.
- Return credits use new bound receipt IDs and current capacity at the original source. Missing/full/unloaded storage
  waits with accountable escrow. Ambiguous physical payment or cargo evidence is never silently reset or destroyed.
- Receipts may be pruned only after the owning ledger durably acknowledges an irreversible applied operation. Keep
  terminal history/tombstones and strict bounded metadata; unsupported future/corrupt files are never re-encoded as empty.
- Unresolved physical operations must coordinate by actual container positions/identities with treasury payment/refund/
  withdrawal, not only village IDs. Paid transport and cargo use separate namespaces/operation roles even with one parent UUID.

Exact stage names and schema should follow this accountable model, without redundant mutable cargo totals. Metadata-only
ledger tests are distinct from actual fee, inventory, receipt and delivery evidence.
