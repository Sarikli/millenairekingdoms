# Save compatibility and safe version changes

Latest follow-up under verification: [RC.8 upgrades/product picker/capital production](1.2.0_RC8_UPGRADES_AND_INCOME.md). Player upgrades bind an existing non-centre building UUID and next native level; the original pre-upgrade complete building cannot fulfill them. Price scales linearly by target display level, with real materials/builders retained. Network4/order5 (lazy1–4)/audit2 (lazy1); political6/payment1/shipment1 remain unchanged. Capital4-per-completed-level daily production uses the existing ledger. Earlier milestone sections below are historical.

Millénaire Kingdoms keeps the existing political registry at format6. Capital UUID/native type deterministically supplies personality identity; no personality reroll or duplicate migration field is needed. New paid work lives in separately versioned bounded atomic stores, never inferred from old tax debts or natural projects.

Representative fixtures from the original1.1.0 serializer and retained original1.1.1 binary exercise every saved political/economic field through the current loader, serializer and separate JVM. The1.1.1 generator/provenance is retained in verification/1.2.0/dev.7/. All15 original KingdomSavedData serializer/nested class files are byte-identical to the preserved stable1.1.1 artifact (whole-JAR packaging checksums differ). The fixture contains three kingdoms, memberships/revisions, ruler, day42,177 owed deniers, war/peace/truce, one conquest victory/receipt, peace offer, pending join/military mandate and next decision day70. They are representative own-mod SavedData fixtures, not a full old9.0.2 world conversion. Unknown dependency data is not repaired or guessed.

New stores: payment journal1, construction intents4 (strict lazy1/2/3 migration; unpaid player WAITING), shipment/physical operation ledger1, NPC decision history1. Native proof identity1 and nested treasury images2 are retained. Unsupported/future/corrupt stores fail closed without erasing bytes; legacy ambiguous physical operations quarantine. A decision outcome records the initial request, never certifies completed construction/delivery. Refer to individual protocol documents and actual crash matrices.

RC.7 construction format4 is described in the [queue protocol](1.2.0_CONSTRUCTION_QUEUE.md). Legacy1–3 reads do not eagerly rewrite files; the next successful locked mutation writes4 preserving existing identities. RC.6 and earlier cannot read format4. A downgrade requires a matching whole-world backup, including chunks/native metadata/payment/order files; deleting the new index is unsafe.

**A full downgrade from1.2.0 to1.1.1 is not supported.** Unchanged format6 alone does not establish a safe gameplay downgrade:1.1.1 does not track paid construction, held cargo, receipts or new recovery obligations. Back up the whole world before upgrading; restore a matching pre-upgrade whole-world backup to return to1.1.1. Never delete new store files to resolve a pending fee/cargo liability, and never mix snapshots of chunks, native village metadata and transaction files from different times.

If a kingdom/source is captured or destroyed, retirement must precede political publication. Already held cargo remains a visible liability when its original source is no longer authorized; it is not credited to a conqueror or silently deleted. Restoring valid original identity can allow existing recovery; creating a new government does not revive a retired UUID. This conservative case is an explicit limitation, not a successful delivery/refund claim.
