## Executive assessment

The project has substantial real safety mechanisms: authoritative native/political identities, operation-bound physical receipts, strict versioned readers, immutable roll journals, server revalidation and paired/crash/native-runtime evidence. Their complexity is often justified by separate chunk/SavedData/journal persistence boundaries. Simplifying these into a single success boolean would lose safety.

External contribution readiness is weaker. Dense methods, a large package dependency cycle, a 1010-line political registry, historical planning documents presented beside current architecture, stale repository release text and a regression runner tied to old counts make changes hard to review. Bounded job counts do not bound synchronous save latency. The natural 300-day run additionally exposed a missing independent strategic path and misleading expiry diagnostics. No confirmed critical money-duplication or authorization bypass was established by this review; that is a scoped finding, not a proof of absence.

Update loops are registered in MillenaireKingdoms: daily checks 20 ticks; conquest orders/strategic recovery 50 ticks; construction HIGH before original growth; shipments LOWEST; NPC HIGH at configured cadence; consolidation LOWEST with 200 tick recovery and configured new work. Scheduler budgets bound jobs, while each selected job may perform synchronous I/O. Stateless policies are useful; static per-level sessions require lifecycle cleanup and must not become extra durable authority.

## Approved maintenance implementation sequence

1. Complete requested independent strategic execution and regression coverage, retaining original balance/native/physical exclusivity and old operation data.
2. Correct expiry diagnostics; no arbitrary cooldown/probability changes or unproven starvation claims.
3. Refactor consolidation runtime locally, suppress only expected unavailable-capital new-work noise, measure actual synchronous costs and keep recovery guarantees.
4. Improve focused runner/build checks/CI, current architecture/contribution/report templates and release provenance.
5. Run changed-domain and appropriate financial/political/history/native/reopen/process-cut gates; compare with immutable 1.2.0. Produce exact final results and 1.2.1 artifacts only after gates pass. Publish only the new authorized version, never replace 1.2.0.

## Deferred roadmap

For 1.2.x, keep small isolated fixes, explicit save migration fixtures, exact image-attributed test evidence and a short current contributor guide. Preserve older large evidence; a manifest/release-archive migration can be proposed without deletion/history rewriting. For 1.3.0 diplomacy, first extract political read models/ports and split codecs from validation while preserving atomic publish/retirement/history order. Design measured targeted/asynchronous durability with immutable server-thread snapshots only if it retains chunk/journal acknowledgment; do not asynchronously access worlds or inventories. Revisit physical/strategic partial-load handoff and large-world indexes with lifecycle tests before new diplomatic features.

Legacy income needs its own producer UUID, journaled owed entitlement and same-container credit receipt, with a persisted once-only ledger acknowledgment. Plan any new registry field as a strict lazy migration, never infer payment from coincidental coin totals or reuse spending/refund intents. Exercise real process cuts before credit, after credit, before owed decrement and after acknowledgment, including native inventory interference and unloaded/captured capitals. That is a separate financial protocol change;1.2.1 does not claim to fix arbitrary-crash income conservation.

## Testing, threading and build assessment

The existing GameTests are valuable integration/domain checks, not a JUnit unit suite: the regular Gradle `test` task is `NO-SOURCE`. Controlled financial/native-record fixtures make both outcomes and interruption boundaries reproducible. They do not prove automatic day scheduling, natural population evolution, graphical behavior or authenticated login. The retained 300-day observation exposed precisely that difference. Several fixtures share one suite world and remove native villages while historical political records remain; isolated suite worlds limit cross-package contamination, but do not make every method independent.

The new original-native independent fixture creates original villages and residents, sets its disclosed hostile relationship, releases setup chunk tickets, and observes normal events with default campaign probability and real RNG. It has a bounded diagnostic deadline. It is separate from both controlled dice tests and the unmodified natural 300-day world. The random ordinary-order test accepts either legitimate result; it checks authority, receipts and absence of forced chunk loads rather than assuming a lucky roll. Process-cut fixtures deliberately choose a committed winning roll so each durable recovery boundary is exercised; they do not claim naturally won gameplay.

Source review keeps world/entity/inventory access on the server thread and client class entry points on client handlers. Existing static sessions use weak level maps or server-stop clearing. Payload bounds and action revalidation remain, but no exhaustive malformed-packet fuzz campaign, all-client lifecycle proof or thread-sanitizer run is claimed. Expected invalid user filter input is silently ignored in ChronicleFilterScreen; malformed localized text falls back in KingdomScreen. Those presentation fallbacks are distinct from financial failures, which retain evidence and diagnostics.

Gradle dependencies/toolchain and the original native checksum remain pinned. Reproducible ZIP ordering/timestamps already existed in 1.2.0. The new packaging check verifies Java 21 class versions, addon-only production classes, version metadata and the exact preserved MIT license; it is basic static/package validation, not a general Java correctness analyzer. Compiler deprecation warnings remain. No new dependency, mass formatter, native JAR change or durability shortcut was introduced. The focused runner now has an actual wall deadline, process-group termination and fail-fast behavior, including failed reloads; a passing write never masks a failed reopen.
