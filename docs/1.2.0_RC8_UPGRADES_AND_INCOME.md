# RC.8 — building upgrades, shipment product picker and capital production

## Royal upgrades

Inside **Rulership → Construction**, a ruler can choose a real completed building's next original level. An upgrade row names the native plan, target display level and building coordinates so identical plans remain distinguishable. The original town hall/centre and town-hall plan sets are excluded. Native walls, disabled upgrades, final-level buildings and unmet original build conditions remain unavailable. New NPC investment policy is unchanged: this additional right is for player rulers.

The administrative price is **current construction base fee × target display level**. Original native plan level0 is display level1; the first upgrade to native1/display2 costs two base fees. With the existing64-denier base:

| Work | Support fee |
|---|---:|
| New building, display level1 |64 deniers (1 silver)|
| Upgrade to display level2 |128 deniers (2 silver)|
| Upgrade to display level3 |192 deniers (3 silver)|
| Upgrade to display level4 |256 deniers (4 silver)|

Linear scaling keeps each step one existing64-denier fee higher; exponential doubling would compound the native plans' already increasing material cost. Real original material requirements are still separate. Server settings can change the base; a reviewed saved order retains its accepted fee, exact building UUID, variant, native plan and target level. A stale offer cannot silently select a different target/level, even if a later fee happens to match.

The original village remains autonomous. The order publishes the original `PendingProject` with `isUpgrade=true`, the existing `BuildingId` and its exact next level; the native engine and actual villagers perform the work. There is no instant status/cursor/block change, supplied material, replacement building or ownership conversion in production. One active royal slot per village includes upgrades. Existing ordinary work is preserved; a waiting upgrade is unpaid and persistent until the original online ruler/current authority, loaded target/treasury, current native eligibility and actual funds allow acceptance. Cancelling an unpaid waiting upgrade is free. Durable accepted patronage retains its fee under the existing policy. If native development changes the target while waiting, the old mandate cannot buy the next level at the old price; it remains unpaid/ineligible until cancelled/reviewed.

Tracking identifies an upgrade by that existing UUID **and** at least the paid target level, with credible original task evidence and actual physical/native persistence before completion. The pre-upgrade complete building is not fulfillment. Interrupted publication remains explicit recovery instead of guessing another debit/refund. Audited recovery can adopt only the same legitimate upgrade target.

## Shipment product selection

Clicking the selected shipment product opens a scrollable list of the server's available source products. Every row draws the actual Minecraft/Millénaire item icon and localized item name. Search accepts a name or registry identifier. Clicking a row selects it and returns to Shipping; Back/Esc returns without changing selection. The existing bounded128-product source preview and server checks remain. This is a selection UI; stock protection, source/destination authorization, fees, cargo and timing are unchanged. A product removed while the list was open is revalidated on the server.

## Capital production

Every active, living kingdom's capital now earns **4 deniers per completed centre level per Minecraft day**, in addition to attached villages' existing4-denier-per-level contributions. A kingdom with no attached villages still produces income:

| Completed capital level | Capital production/day |
|---|---:|
|1|4 deniers|
|2|8 deniers|
|3|12 deniers|
|4|16 deniers|

The shared rate keeps a capital's own production comparable to one same-level member village. It does not multiply taxation or alter prices, reputation thresholds, NPC reserve/share rules, political probabilities or RC.5 timers. A level1 capital plus two level1 members now produces12/day instead of8; one level3 capital alone produces12/day. A planned/unbuilt centre produces0. During a native centre upgrade, only the already completed level counts; extra income starts on completion. Royal centre upgrades remain prohibited.

Capital production joins the existing daily income snapshot and day marker, then reaches real original capital chests in original coin denominations. It uses the same once-per-booked-day/restart/backward-time/skip behavior; there is no separate repeating mint timer. Full/unloaded storage keeps undelivered entitlement in the existing ledger and never forces chunks. Inactive/fallen kingdoms do not earn new income. Membership is counted once, so a conquered former capital does not keep a second capital bonus. Existing owed balances and the already booked day are retained; adopting RC.8 does not retrospectively mint earlier days. Normal restart evidence is separate from arbitrary power-loss atomicity, which is not newly promised.

## Compatibility and scope

Matching client/server builds require **network protocol4** so older clients cannot misinterpret an upgrade as a new-building offer. Construction intents advance to **format5**, strictly/lazily reading1–4; recovery audit advances to **format2**, reading1. Upgrade target/level fields are accepted only under their new formats. Existing new-building fields, financial identities, terminal/cancellation/recovery provenance and unknown/future bytes are preserved. Political format6/payment1/shipment1/NPC history remain unchanged. Back up the whole world before upgrading. Earlier candidates cannot read the new formats; downgrade requires a matching whole-world backup, not deleting transaction files.

Original Millénaire9.0.3 remains separate and unmodified. No environment configuration, setup script or startup instructions change. GUI rendering/input/scaling and authenticated online login require separate manual checks; automated server results alone do not verify them. The separate user's Norman1047 cobblestone/0 sendable cause remains open; this work does not reduce native stock protection or speculate about that save.
