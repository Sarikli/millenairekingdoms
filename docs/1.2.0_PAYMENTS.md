# Royal payments: implemented boundary and policy

`RoyalPaymentService` debits actual loose Millénaire coins from the capital's existing, loaded town-hall chests.
It is an internal server service; no GUI packet or NPC scheduler calls it yet. Owed taxes never count as funds.
Player entry points use existing ruler/reputation checks. NPC entry points only accept kingdoms without a player ruler.
Both recheck authority, capital, physical storage and complete slot contents immediately before mutation.

Each immutable intent binds a request UUID, dimension, kingdom, capital, player UUID (or NPC agency), purpose,
domain reference UUID and positive amount. Domain services must compute prices on the server and persist their own
order/reference lifecycle. A caller may fulfill only a `PAID` receipt for that exact purpose/reference; merely getting
a receipt, or finding `PREPARED`, is not payment. Reusing an ID with a different intent is rejected.

## Physical save protocol

1. Quote loaded, deduplicated physical chest halves; reject stale/replaced/reconnected containers.
2. Plan exact change separately within each 27-slot chest. A debit never increases any chest's coin value.
   No money moves between independently saved chests. A chest unable to make its allocated change is skipped;
   if remaining chests cannot cover the expense, reject without taking anything.
3. Assign versioned UUIDs in the chests' NeoForge persistent data. Serialize only their already loaded chunks using
   Minecraft's `ChunkSerializer`, including its normal `ChunkDataEvent.Save`. Await actual write futures, flush the
   region worker, then read back saved block states, block entities, UUIDs and all slots.
4. Durably write `PREPARED` with complete versioned before/after images before changing any coins.
5. Revalidate authority/storage/slots and apply on the server thread. Invalidate Millénaire's inventory cache.
6. Repeat acknowledged writes, flush and disk read-back; also require the live after image. Only then write `PAID`.

This bypasses the exception-swallowing convenience `ChunkMap.save` path, not Minecraft's serialization format.
It leaves chunks dirty for ordinary later saves and never loads or forces a distant chunk. Full-world saves are not
required for each payment. Journal replacement/locking and directory sync are atomic primitives on the tested Linux
filesystem. Chunk and journal files still have no common atomic commit.

If interrupted in `PREPARED`, an exact request retry checks every original chest identity, connection and full contents.
Each must match its own before or after image. Mixed independently saved chunks roll forward to the recorded after
images, then pass the same persistence barrier before `PAID`. Debit images are monotone per chest, so a partial chunk
save cannot temporarily create coins by moving change from an unsaved chest to a saved one.

## Fulfillment, cancellation and failure policy

- `PAID` means an expense is reserved but its domain action has not yet been durably accepted. It blocks a different
  payment for the same capital. This is a short acceptance barrier, not a lock for the lifetime of a construction job.
- After durably accepting its action, a domain service explicitly commits the receipt. `COMMITTED` is nonrefundable
  administrative expenditure. Retrying commit or the original payment returns the existing receipt without more coins.
- Before fulfillment, cancellation refunds a `PAID` payment. Credit exactly the original amount taken from each
  original physical chest, added to CURRENT stock; preserve later deposits, goods and custom coins. Persist a complete
  `REFUND_PREPARED` image before mutation and acknowledge it by the same barrier before `REFUNDED`.
- A repeated refund never credits twice. A failed/partially saved refund rolls forward using its own before/after
  images. Refunds never decrease a chest's value or shift existing money between chunks.
- Cancellation may also start from `PREPARED`: reconcile that exact debit before refunding, so an unsaved debit never
  produces a free credit. If interrupted after `PAID` but before refund preparation, retry cancellation. A future domain
  service must persist its cancellation decision and must not fulfill a cancelled order merely because payment is PAID.
- Full refund storage retains `PAID`; retry after space is available. Unloaded storage defers without chunk forcing.
- If authority is lost, the capital/kingdom is gone, or the original player is no longer authorized, reject the action
  and retain the journal/reservation. Never refund to a new ruler's different treasury or invent a replacement chest.
- Replaced/reconnected/changed storage or a third unexpected slot image is quarantined as `RECOVERY_REQUIRED`, with a
  position/reason in the journal. Preserve physical contents, all before/after images and the reservation. Automatic
  reset, speculative rollback, new-ID bypass and automatic refund are forbidden. Resolving this ambiguous case needs
  a separately audited operator/backup recovery procedure; that procedure is not implemented yet.
- A failed write/flush/read-back/journal acknowledgement returns no successful paid receipt. The existing intent
  remains available for exact retry. Future/corrupt formats are preserved and fail closed.

## Evidence and limits

The current dev.2 focused package passed **46 required tests in the write JVM and 46 in a separate reload JVM**, in a fresh
world; normal build passed. Evidence: `verification/1.2.0/dev.2/`. The earlier coordinator checkpoint was 41+41.
It covers real coins/chests/goods, conflicts/replay, reservations, player/NPC authority, full/unloaded storage,
replacement, actual journal locks, stale disk read-back, failed final acknowledgement and refund retry.
Three persistent fixtures use the original `millenaire:byzantines/archives_a_0` plan metadata so Millénaire itself
rehydrates their inventory after restart; no post-load metadata repair is performed. They test mixed chunks, durable
debit before `PAID`, and durable refund before `REFUNDED`. They are inventory fixtures, not evidence of NPC construction.

Four actual abrupt JVM termination boundaries were subsequently verified in four fresh worlds/12 JVMs.
Preparation and recovery each logged `All 1 required tests passed`; halted JVMs deliberately failed with exit 70 and no
GameTest pass line. Before/partial/after/refund disk values were 128/96/64/128; recovered values were 64/64/64/128.
See `verification/1.2.0/payment-crashes/`. Power loss, other filesystems, hostile external mods/editors and automatic
recovery from third-party inventory interference remain unverified. No paid gameplay is exposed yet. Domain order/payment
crash coordination, diagnostic UI/operator recovery and long-run performance remain integration work. The reservation scan
currently reads historical records on each new expense; measure/index this before a large NPC simulation.

## Server-owned prices

The `[royalEconomy]` section of the existing per-world server config now defines positive construction/base-shipment
fees and nonnegative distance/load fees. It does not change the tax formula or pay for construction materials.
Default patronage is 64 deniers (one silver coin). Default shipment logistics:
`4 + ceil(horizontal distance / 128) + ceil(item quantity / 64)` deniers. Thus 64 items over 256 blocks cost 7;
65 items over 257 blocks cost 9. Reject nonpositive quantities, negative distances and overflow. Domain services must
derive membership, quantity and distance from real server data, then freeze the accepted quote in the order's intent.
A config change affects new quotes, never the price bound to an existing payment ID.

Existing income remains 4 deniers per completed town-hall level per attached non-capital village per Minecraft day.
64-denier patronage therefore costs 16 level-days: eight days from one level-2 member or about 2.67 days from three
level-2 members. A 7-denier shipment costs 1.75 level-days. These are conservative starting prices, not completed NPC
reserve/cooldown balancing or evidence of hundreds of simulated days. Domain consumers and balance gates remain.
