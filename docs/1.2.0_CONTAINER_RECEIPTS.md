# Native operation receipts and the reproduced money-recovery bug

The former image-only payment protocol was insufficient after normal inventory activity. A real fixture in
`35f7adb` paid64 out of128, saved its64 refund but lost the journal acknowledgement, then used original9.0.3
`BuildingInventory.remove` to move64 to a second actual chest. Retrying the refund treated the coinciding old BEFORE
image as unpaid and minted64: capital128 + recipient64 =192 instead of128. The failed GameTest is preserved under
`verification/1.2.0/receipt-interference/`; it is not passing evidence. No claim that an actual merchant goal ran.

## Implemented correction

The original persistent container identity key `millenairekingdoms:royal_treasury` stays format1. Financial journal
format1 and political6/order3 also stay unchanged. New **nested treasury images use format2**, binding the parent payment
UUID, full immutable intent and DEBIT/REFUND role. Every changed physical chest receives a deterministic operation UUID
and full binding (parent, intent including dimension/agency/capital/purpose/reference/amount, role, physical UUID,
position and that chest's coin delta).

The native chest's NeoForge persistent data key `millenairekingdoms:royal_operations`, format1, holds up to256 proofs.
Only loaded original containers participate. All metadata/capacity/identities/slots are preflighted before slot mutation.
On the server thread the coordinator writes slots and their proof without yielding or serializing between them.
Minecraft's ordinary block-entity/chunk serializer then saves **Items and proof together**. Acknowledged chunk writes,
worker flush and read-back verify the actual intended contents AND matching proof before the financial journal moves.
No new Mixin, dependency modification, separate physical-proof file or forced chunk loading.

- Matching proof: the operation already applied. Preserve CURRENT slots, including legitimate subsequent NPC consumption,
  deposits and goods edits. Do not restore old after/before images or apply its delta again.
- No proof: only exact BEFORE is safe to mutate. An unreceipted after/third image is quarantined; amount equality alone
  never proves application. Untouched chest halves preserve current contents and need no new proof.
- Identity/block-state/storage replacement, mismatched proof binding, duplicate IDs, malformed/future/unknown metadata
  fail closed. Preserve unknown data and actual slots. No guessed rollback or financial operator reset.
- Only after durable PAID/REFUNDED acknowledgement may the owning proof be removed and its chunk saved. Cleanup failure
  logs a warning but cannot undo/report failure for an acknowledged expense. The journal retains permanent request
  history. A crash can leave a stale acknowledged proof; it is safe to retain and does not make funds reusable. There
  is no automatic global sweep;256 retained proofs per chest is a hard fail-closed bound, not unbounded growth.

## Legacy pending images

Already acknowledged legacy PAID/COMMITTED/REFUNDED records retain their financial meaning. A legacy PAID refund uses
its original per-chest debit entitlement with a NEW format2 refund/proof. **Legacy PREPARED/REFUND_PREPARED images have
no durable operation proof. They are preserved and quarantined even if counts match BEFORE or AFTER.** No speculative
migration can distinguish native activity from an unapplied operation. Existing audited construction recovery does not
reset ambiguous financial journals. Inspect/restore an authentic backup or retain the liability for explicit reviewed
recovery; never erase/recreate the request under a fresh UUID to bypass it.

## Validation and limits

Focused `verifyRoyalReceipts` covers the actual192->128 refund reproduction, native deposits restoring old debit counts,
receipted third images/unrelated goods, missing/corrupt/future/colliding proofs, strict full image binding, legacy pending
quarantine/acknowledged refund, post-ack cleanup write failure, and actual native activity/proof surviving separate JVMs.
The existing economy/consumer gates and actual abrupt-process probes are separately recorded with real pass lines.
Intentionally halted processes never count as passed GameTests. This is ordered process-crash protection on the tested
filesystem/native serializer, not host-power-loss/whole-world atomicity or arbitrary external-editor/mod protection.
No live goods transfer follows merely from implementing money receipts; shipment escrow/lifecycle remains a separate gate.
